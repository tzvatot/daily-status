# Daily Status - 2026-09-02

## Accomplishments

- **Validated the PROGRESSING condition fix on a deployed operator image** for [OSAC-4441](https://redhat.atlassian.net/browse/OSAC-4441) ([osac#646](https://github.com/osac-project/osac/pull/646)): deployed a dev/kind OSAC environment on a lab server using the PR operator image, seeded the required catalog prerequisites (HostType, ClusterVersion, ClusterTemplate), created a real Cluster and ClusterOrder CR, then wrote and ran a scripted validation harness that patches CR conditions in varying array orders and asserts the synced Cluster PROGRESSING reason/message. All 4 test cases passed — confirming the deployed code derives the furthest-reached provisioning stage by fixed rank, independent of condition array order, matching the controller unit tests exactly.
- **Resolved infrastructure issues during dev/kind deployment**: diagnosed and fixed PID exhaustion on the kind cluster node caused by high Go thread counts on a 96-vCPU host, which was crash-looping multiple OSAC pods. Stabilized all pods to zero restarts.
- **Prepared for real end-to-end validation via caas-ci**: received the AAP license from Guy; identified and adopted Guy's proven `ice-osac/osac-standalone` tooling for standing up a full OpenShift SNO + caas-ci OSAC environment on the lab server; built and pushed the PR operator image to a public quay.io registry so the SNO cluster can pull it without extra credentials.
- **Began executing the caas-ci deployment** on the lab server: kicked off the automated redeploy flow and worked through two blockers — the host's RHEL subscription is expired (preventing package installs), so bootstrapped Ansible via pip and sourced `virt-install` from a temporary Rocky 9 repo. Deployment progressed through the nuke and into VM creation before hitting the second blocker; cleanup and re-run are next.

## Risks & Challenges

- The dev/kind validation uses synthetically patched CR conditions rather than conditions written by a real provisioner. While the controller cannot distinguish synthetic from real conditions, true end-to-end proof requires a full caas-ci install with AAP and HyperShift, which is still in progress.
- The lab host's RHEL subscription is expired and cannot be re-registered without the host owner's credentials, forcing workarounds for every missing system package.
- The existing caas-ci e2e tests assert cluster state transitions and node scaling but do not assert PROGRESSING reason/message granularity — a new assertion would be needed to exercise this change in CI.

## Key Effort

Deploying and validating the order-independent PROGRESSING condition derivation fix ([OSAC-4441](https://redhat.atlassian.net/browse/OSAC-4441)) on a real OSAC environment, first via dev/kind with synthetic conditions (completed, all assertions passed), and then preparing a full caas-ci deployment for real provisioner-driven validation (in progress).
