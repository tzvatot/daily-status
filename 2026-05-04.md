# Daily Status - 2026-05-04

## Accomplishments

- **CaaS demo environment — re-published templates with latest changes from [osac-aap#274](https://github.com/osac-project/osac-aap/pull/274):** Synced AAP project to latest main, re-ran publish-templates job, and verified that cluster templates no longer expose sensitive parameters directly. Confirmed cluster creation works with the new explicit secret-file flags and that secrets are properly redacted.

- **Fixed osac-operator crash loop on vmaas-dev:** Diagnosed an informer cache sync timeout caused by missing RBAC permissions for the PublicIP resource. Patched the operator's ClusterRole and updated the operator image to latest main — all controllers now syncing successfully.

- **Fixed AuthConfig tenant assignment:** Cluster creation was failing because all service accounts were incorrectly assigned to multiple tenants. Corrected the configuration so only the template-publisher service account gets cross-tenant access, while other accounts are scoped to their own namespace. Demo cluster creation resumed successfully.

- **Fixed Ansible role resolution failure ([osac-aap#282](https://github.com/osac-project/osac-aap/pull/282)):** AAP cluster provisioning jobs were failing because an Ansible role was referenced by short name instead of its fully qualified collection name, a regression introduced during the Netris integration work ([MGMT-23420](https://issues.redhat.com/browse/MGMT-23420)). Fixed all references, deployed to vmaas-dev, verified the fix, and merged the PR.

- **Cleaned up stale ESI routers to resolve router quota exhaustion:** AAP provisioning was blocked by a full router quota. Identified and deleted 5 orphaned routers that had no matching cluster orders in Kubernetes, freeing up capacity. Retried cluster creation — provisioning now progresses past router creation.

## Risks & Challenges

- **Cluster provisioning blocked on agent availability:** After clearing the router quota issue, cluster creation fails because all bare-metal agents of the required resource class are bound to an existing cluster order. Need to either free those agents or relabel unassigned agents before the demo cluster can complete provisioning.
- **Potential bug in cluster teardown — orphaned routers:** Four of the five stale routers had no matching cluster order in Kubernetes, suggesting that router cleanup during cluster deletion may not be reliable. If the cluster order CR is removed before the deprovision job completes (or the job fails), routers are orphaned. This needs investigation to determine if the operator's finalizer-based cleanup is sufficient.

## Key Effort

Unblocking end-to-end CaaS cluster provisioning on the vmaas-dev environment by fixing a series of cascading issues — operator crashes, tenant misconfiguration, Ansible role resolution, and infrastructure quota exhaustion.
