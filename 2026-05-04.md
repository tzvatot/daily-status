# Daily Status - 2026-05-04

## Accomplishments

- **Re-published CaaS demo templates** after syncing to latest main (which includes [osac-aap#274](https://github.com/osac-project/osac-aap/pull/274)). Verified that the small OCP template no longer exposes secret parameters directly, and that cluster creation works correctly with the new explicit secret-file flags.
- **Fixed osac-operator crash loop on vmaas-dev** — diagnosed a missing RBAC permission for the PublicIP resource that was causing informer cache sync timeouts. Patched the cluster role and updated the operator to the latest image; all controllers are now syncing normally.
- **Fixed AuthConfig tenant assignment** — cluster creation was failing because all service accounts were being assigned to multiple tenants instead of just one. Corrected the configuration so only the template-publisher SA gets the shared tenant. Successfully created a new demo cluster order.
- **Fixed broken Ansible role reference** ([osac-aap#282](https://github.com/osac-project/osac-aap/pull/282)) — an AAP job was failing because a role introduced in the Netris work ([MGMT-23420](https://issues.redhat.com/browse/MGMT-23420)) was referenced by short name instead of its fully-qualified collection name. Fixed, deployed, verified, and merged.
- **Cleaned up stale ESI routers** — router quota was exhausted, blocking new cluster creation. Identified and deleted 5 orphaned routers that had no matching cluster orders. Retried cluster provisioning, which now gets past router creation but is blocked on agent availability.

## Risks & Challenges

- **Blocked on bare-metal agent availability:** All agents of the required resource class are currently bound to an existing cluster order. No agents are free for new cluster provisioning until that order is deleted or unassigned agents are relabeled.
- **Potential bug in cluster teardown:** Four of the five orphaned routers had no matching cluster order in Kubernetes, suggesting that router cleanup during cluster deletion may not be reliable — possibly due to finalizer or partial-failure handling issues in the deprovision job.

## Key Effort

Unblocking the CaaS demo environment by fixing a chain of issues (operator crash, tenant misconfiguration, broken Ansible role, and router quota exhaustion) across the vmaas-dev deployment.
