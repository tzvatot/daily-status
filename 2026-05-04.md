# Daily Status - 2026-05-04

## Accomplishments

- **CaaS demo environment — re-published templates with latest changes from [osac-aap#274](https://github.com/osac-project/osac-aap/pull/274):** Synced AAP project to latest main, re-ran publish-templates job, and verified that OCP templates no longer expose sensitive parameters directly. Tested cluster creation with explicit secret file flags — working correctly with redacted secrets.

- **Fixed osac-operator crash loop on vmaas-dev:** Diagnosed an informer cache sync timeout caused by missing RBAC permissions for the PublicIP resource. Patched the cluster role and updated the operator to latest main — all controllers now syncing successfully.

- **Fixed AuthConfig tenant assignment:** Cluster creation was failing because all service accounts were incorrectly assigned to multiple tenants. Corrected the configuration so only the template-publisher SA gets cross-tenant access, while other SAs are scoped to their own namespace. Demo cluster creation resumed successfully.

- **Fixed missing Ansible role reference — [osac-aap#282](https://github.com/osac-project/osac-aap/pull/282):** AAP provisioning jobs were failing because a role was referenced by short name instead of its fully qualified collection name, introduced during the [MGMT-23420](https://issues.redhat.com/browse/MGMT-23420) Netris integration. Fixed the references, deployed to vmaas-dev, verified the fix, and merged the PR.

- **Cleaned up stale ESI routers (router quota exceeded):** Provisioning was blocked by a full router quota. Identified and deleted 5 orphaned routers that had no matching cluster orders in Kubernetes. After cleanup, retried cluster creation — provisioning progressed past router creation but is now blocked on agent availability.

## Risks & Challenges

- **Blocked on agent availability:** No bare-metal agents of the required resource class are currently free — all are bound to an existing cluster order. Need to either free up agents or relabel unassigned ones before cluster provisioning can complete.
- **Potential router leak bug:** 4 of the 5 orphaned routers had no matching cluster order in Kubernetes, suggesting that if a cluster order CR is deleted before the deprovision job completes (or the job fails), routers are orphaned. The operator's finalizer-based cleanup and the ESI teardown job's partial failure handling need investigation.

## Key Effort

Unblocking the CaaS demo environment on vmaas-dev by fixing a series of cascading issues — operator crashes, tenant misconfiguration, Ansible role resolution, and infrastructure quota exhaustion — to get end-to-end cluster provisioning working.
