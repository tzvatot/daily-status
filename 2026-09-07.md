# Daily Status - 2026-09-07

## Accomplishments
- Merged [osac#767](https://github.com/osac-project/osac/pull/767) (approved by Riccardo).
- Investigated why a one-worker HyperShift cluster was stuck progressing despite a healthy hosted control plane. Confirmed that guest-cluster operators (image-registry, ingress, monitoring) could not schedule because the infrastructure availability policy was set to HighlyAvailable, requiring replicas that a single worker cannot satisfy.
- Traced the root cause to the standalone deployment configuration: the standalone recipe unconditionally injects HighlyAvailable for HyperShift deployments, overriding the CI template's SingleReplica fallback. Confirmed the full policy-precedence chain from the deployment overlay through the AAP configuration to the resulting HostedCluster spec.
- Applied an immediate workaround by patching the AAP configuration to explicitly set the infrastructure availability policy to SingleReplica.
- Replaced the blocked test cluster with a new one and verified that the new HostedCluster correctly reflects SingleReplica for both controller and infrastructure availability policies.

## Risks & Challenges
- The standalone deployment recipe still defaults infrastructure availability to HighlyAvailable for HyperShift, which is incompatible with single-worker CI topologies. A decision is needed on whether to default to SingleReplica or expose an explicit per-deployment setting.
- The replacement test cluster still needs to be monitored through full availability to confirm that a single-worker configuration completes successfully with the corrected policy.

## Key Effort
Investigated and worked around a one-worker HyperShift cluster availability failure caused by a misconfigured infrastructure availability policy in the standalone deployment recipe.
