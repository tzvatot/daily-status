# Daily Status - 2026-09-07

## Accomplishments

- **Investigated one-worker HyperShift cluster availability issue** ([OSAC-4441](https://redhat.atlassian.net/browse/OSAC-4441)): Diagnosed why a single-worker hosted cluster remained stuck in a progressing state. The hosted control plane was healthy, but guest-cluster infrastructure operators (image-registry, ingress, monitoring) could not schedule because the infrastructure availability policy was set to `HighlyAvailable`, requiring replicas that a single worker cannot satisfy. Traced the root cause to the standalone deployment overlay, which explicitly injects a high-availability infrastructure policy that overrides the CI template's single-replica fallback. Applied an immediate workaround by patching the configuration to use single-replica infrastructure policy, and verified that a replacement cluster was created with the correct policy and successfully reached a ready state.
- **Retested merged [osac#767](https://github.com/osac-project/osac/pull/767) in a live deployment**: After [osac#767](https://github.com/osac-project/osac/pull/767) was approved and merged, deployed the merged operator image to the validation environment. Confirmed the previous test cluster completed successfully, then tore it down and created a fresh cluster to validate the merged code's semantic sub-stage feedback transitions. Initial lifecycle feedback is reporting the expected progression messages. Monitoring continues through terminal state.
- **Reported cluster-storage finalizer retention bug to the storage working group**: After deleting a test cluster, observed that the cluster order remains stuck in a deleting state because the storage finalizer is never removed, even though all other cleanup (HyperShift teardown, deprovisioning job, feedback cleanup) completed successfully. Shared the issue, evidence, and reproduction steps with the storage team. The likely cause is that deletion events are not reliably triggering the storage reconciliation path.

## Risks & Challenges

- The standalone deployment recipe defaults infrastructure availability to high-availability for HyperShift mode, which is incompatible with one-worker CI topologies. A configuration fix is needed to align standalone defaults with the upstream CI values or expose an explicit per-deployment setting.
- The cluster-storage finalizer retention bug can leave deleted cluster orders stuck indefinitely. This requires a storage-controller investigation and fix rather than manual finalizer removal.

## Key Effort

Investigated and resolved a one-worker HyperShift cluster availability blocker caused by a mismatched infrastructure availability policy, and validated the merged lifecycle feedback feature in the corrected environment.
