# Daily Status - 2026-09-07

## Accomplishments
- Merged [osac#767](https://github.com/osac-project/osac/pull/767) after approval.
- Investigated why a one-worker HyperShift cluster was stuck progressing despite its hosted control plane being fully healthy. Determined that guest-cluster operators (image-registry, ingress, monitoring) could not schedule their HA replicas on a single worker node because the infrastructure availability policy was set to highly-available instead of the intended single-replica mode.
- Traced the root cause to the standalone deployment recipe, which unconditionally injects a highly-available infrastructure policy for HyperShift deployments, overriding the single-replica fallback defined in the CI cluster template. Confirmed the full policy-precedence chain from the deployment overlay through the automation platform configuration.
- Applied an immediate workaround by explicitly setting the infrastructure availability policy to single-replica in the deployment configuration.
- Replaced the stuck test cluster with a new one and verified that the replacement cluster was created with single-replica policies for both controller and infrastructure, confirming the override takes effect for newly created clusters.

## Risks & Challenges
- The standalone deployment recipe still defaults to highly-available infrastructure policy for HyperShift mode, diverging from the upstream CI configurations that use single-replica. A permanent fix is needed to either default to single-replica for one-worker CI topologies or expose an explicit per-deployment setting.
- The replacement cluster is still being monitored to confirm it reaches a fully available state end-to-end with the single-replica infrastructure configuration.

## Key Effort
Investigated and worked around a one-worker HyperShift cluster availability failure caused by a misconfigured infrastructure availability policy in the standalone deployment recipe.
