# Daily Status - 2026-09-07

## Accomplishments

- **Investigated one-worker HyperShift cluster availability issue:** Diagnosed why a single-worker CI cluster remained in a progressing state despite a healthy hosted control plane. Root cause: the infrastructure availability policy was set to HighlyAvailable, causing data-plane services (ingress, image registry, monitoring) to require multiple replicas that cannot schedule on a single worker node. Traced the policy precedence through the standalone deployment configuration and confirmed the CI-specific fallback was being overridden by an explicit HighlyAvailable injection in the standalone overlay.
- **Applied workaround for the one-worker policy issue:** Patched the active configuration to use SingleReplica for infrastructure availability, replaced the stuck test cluster, and verified new clusters are created with the correct single-replica policy. A permanent fix to the standalone deployment recipe is still outstanding.
- **Merged [OSAC-4441](https://redhat.atlassian.net/browse/OSAC-4441) Story 1.02 lifecycle semantic sub-stages PR:** [osac#767](https://github.com/osac-project/osac/pull/767) was approved and merged.
- **Deployed and began retesting the merged Story 1.02 changes:** Built and deployed the merged operator image to the validation environment. Confirmed the prior test cluster reached full readiness, then created a fresh cluster to validate the new semantic sub-stage feedback end-to-end. Initial sub-stage transitions are being observed; monitoring continues through the terminal ready state.
- **Reported cluster-storage finalizer retention bug to the storage working group:** After deleting a test cluster, the backing order remains stuck in a deleting state because the storage finalizer is not removed, even though all other cleanup (HyperShift teardown, deprovisioning job, feedback cleanup) completed successfully. Shared reproduction steps and evidence with the storage team. The likely cause is that the owner tenant's storage reconciliation is not being triggered reliably on cluster order deletion.

## Risks & Challenges

- The standalone deployment recipe defaults infrastructure availability to HighlyAvailable for HyperShift, which breaks one-worker CI topologies. A workaround is in place but a permanent configuration fix is still needed.
- The cluster-storage finalizer retention bug causes deleted cluster orders to remain indefinitely in a deleting state. This requires investigation by the storage team and should not be worked around by force-removing the finalizer.

## Key Effort

Investigated and resolved a one-worker HyperShift cluster availability issue caused by an incorrect infrastructure availability policy, and began end-to-end validation of the merged [OSAC-4441](https://redhat.atlassian.net/browse/OSAC-4441) lifecycle semantic sub-stages feature.
