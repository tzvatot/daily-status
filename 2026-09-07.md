# Daily Status - 2026-09-07

## Accomplishments

- **Investigated one-worker HyperShift cluster availability failure.** Diagnosed why a single-worker CI cluster could not reach available state: guest-cluster infrastructure services (ingress, image-registry, monitoring) required HA replicas that could not be scheduled on a single node. Root-caused the issue to the standalone deployment overlay injecting a HighlyAvailable infrastructure availability policy, which overrides the CI template's SingleReplica fallback due to environment-variable load ordering. Applied an immediate workaround to the deployment configuration and verified that a newly created cluster correctly received SingleReplica for both availability policies. A standalone recipe configuration fix is still needed to align with upstream CI defaults.
- **Retested [OSAC-4441](https://redhat.atlassian.net/browse/OSAC-4441) Story 1.02 semantic sub-stage feedback after [osac#767](https://github.com/osac-project/osac/pull/767) was merged.** Deployed the merged operator image to the validation environment, confirmed the previous test cluster reached full availability, then created a fresh cluster to validate post-merge sub-stage transitions. Initial feedback correctly reported the first semantic sub-stage. Monitoring through remaining transitions is still in progress.
- **Reported a cluster-storage finalizer bug blocking CaaS cluster deletion.** After deleting a test cluster, the backing order remained stuck in Deleting because the storage finalizer was never removed, even though all other cleanup (HyperShift teardown, AAP deprovision job, feedback finalizer) completed successfully. Shared the reproduction flow and evidence with the storage working group. The likely cause is that the owner tenant's storage reconciliation is not reliably enqueued when a cluster order is deleted.

## Risks & Challenges

- The storage finalizer bug leaves deleted cluster orders in a Deleting state indefinitely; requires investigation by the storage team.
- The standalone deployment recipe still defaults infrastructure availability policy to HighlyAvailable for HyperShift, which will break any future one-worker CI topology until the configuration is corrected.

## Key Effort

Investigated and worked around a one-worker HyperShift availability failure caused by an infrastructure availability policy misconfiguration, while validating merged semantic sub-stage feedback on a fresh deployment.
