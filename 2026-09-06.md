# Daily Status - 2026-09-06

## Accomplishments

- [OSAC-4441](https://redhat.atlassian.net/browse/OSAC-4441): PR [osac#646](https://github.com/osac-project/osac/pull/646) (order-independent ClusterOrder feedback condition mapping) received LGTM and approval, all CI checks are passing, and hold was removed — waiting for auto-merge to trigger.
- [OSAC-4441](https://redhat.atlassian.net/browse/OSAC-4441): Validated the PROGRESSING feedback behavior on a real OSAC deployment (caas-ci host). Two test scenarios passed, confirming the operator correctly derives the furthest provisioning stage from ClusterOrder conditions and syncs the expected state back to the fulfillment service.
- Set up a full OSAC development environment on a caas-ci host: deployed all OSAC components via Helm, registered a bare-metal worker agent, installed the OSAC CLI, and seeded cluster templates and versions.
- Resolved three infrastructure blockers during environment setup:
  - Metal3/Ironic was not deployed on the platform-None SNO cluster — created the required Provisioning resource to bring up Ironic.
  - BareMetalHost registration was failing due to an HTTPS/HTTP protocol mismatch with the BMC emulator — corrected the BMC address scheme.
  - AAP job was failing because the pull secret was missing and the AAP service account lacked permissions to read it — created the secret and added the necessary RBAC binding.
- Identified a remaining blocker: AAP cluster creation jobs fail at the networking step because the environment has no OpenStack/ESI backend, and the CI-oriented cluster template incorrectly defaults to the OpenStack-based network path instead of the CI-compatible one. Identified three possible fixes but have not yet applied one.

## Risks & Challenges

- PR [osac#646](https://github.com/osac-project/osac/pull/646) merge depends on CI completing cleanly after the hold was removed — currently all green, expected to auto-merge shortly.
- The AAP networking blocker (missing OpenStack backend) prevents full end-to-end cluster lifecycle validation. A CI-compatible network bypass exists but has not yet been tested on this environment.
- The SNO VM running HyperShift control plane workloads is near memory capacity (~80%), which could cause pod evictions under load.

## Key Effort

Validating the ClusterOrder feedback condition mapping ([OSAC-4441](https://redhat.atlassian.net/browse/OSAC-4441)) on a real OSAC deployment and driving PR [osac#646](https://github.com/osac-project/osac/pull/646) toward merge.
