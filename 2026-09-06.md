# Daily Status - 2026-09-06

## Accomplishments

- [OSAC-4441](https://redhat.atlassian.net/browse/OSAC-4441): PR [osac#646](https://github.com/osac-project/osac/pull/646) (order-independent ClusterOrder feedback condition mapping) received LGTM and approval, all CI checks are passing, and hold was removed — waiting for auto-merge to trigger.
- [OSAC-4441](https://redhat.atlassian.net/browse/OSAC-4441): Validated the PROGRESSING feedback behavior on a real CaaS CI deployment (host karim04). Two test scenarios passed, confirming the operator correctly derives the furthest provisioning stage from ClusterOrder conditions and syncs the expected status back to the fulfillment service.
- Set up and deployed a full OSAC environment on a bare-metal CI host, including the operator running the PR image, Metal3/Ironic infrastructure, a virtual bare-metal worker with agent registration, and the OSAC CLI — enabling real cluster lifecycle testing.
- Resolved three deployment blockers during environment setup:
  - Ironic/Metal3 was not deployed because the SNO cluster (platform type None) required a Provisioning CR to be created manually.
  - BareMetalHost registration was failing due to the BMC address defaulting to HTTPS while the virtual BMC emulator runs plain HTTP — fixed by switching to the HTTP scheme.
  - AAP job was failing because the pull secret was missing and the AAP service account lacked RBAC to read it — fixed by creating the secret and granting access.
- Investigated and documented a remaining blocker: AAP cluster creation fails at the networking step because the environment has no OpenStack/ESI, and the job template is not configured to use the CI-compatible network backend. Identified three potential fixes but have not yet applied one.

## Risks & Challenges

- PR [osac#646](https://github.com/osac-project/osac/pull/646) merge depends on CI completing cleanly after the hold was removed — currently all green and should auto-merge.
- The AAP networking misconfiguration (ESI/OpenStack not available in this CI environment) blocks full end-to-end cluster lifecycle validation. A CI-compatible network backend exists but hasn't been tested on this environment yet — need team input on the correct approach.
- SNO memory utilization is around 80% with HyperShift control plane pods, which may cause pod evictions if additional clusters are created.

## Key Effort

Validating the ClusterOrder feedback condition mapping feature ([OSAC-4441](https://redhat.atlassian.net/browse/OSAC-4441)) on a real CaaS CI deployment while driving PR [osac#646](https://github.com/osac-project/osac/pull/646) toward merge.
