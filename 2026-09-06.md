# Daily Status - 2026-09-06

## Accomplishments

- Merged [osac#646](https://github.com/osac-project/osac/pull/646) for [OSAC-4441](https://redhat.atlassian.net/browse/OSAC-4441) — order-independent ClusterOrder feedback condition mapping. PR received LGTM and approval, all CI checks passed, and it was merged.
- Validated the PROGRESSING feedback feature on a real OSAC deployment (caas-ci environment) by running four end-to-end test scenarios:
  - **T1 & T2**: Confirmed the feedback controller correctly derives the furthest provisioning stage from ClusterOrder conditions on a live cluster.
  - **T3**: Validated the full lifecycle progression — watched PROGRESSING advance through real control plane boot stages (ControlPlaneCreated → ControlPlaneAvailable), confirming the feature works end-to-end on a real HyperShift deployment.
  - **T4**: Confirmed order-independence is naturally validated since the operator sets conditions asynchronously as it observes Kubernetes resources.
- Diagnosed and resolved six deployment blockers on the caas-ci environment to enable end-to-end validation:
  - Deployed Metal3/Ironic by creating the missing Provisioning CR (required on platform-None SNO clusters).
  - Fixed BareMetalHost registration by switching BMC address to HTTP scheme (sushy-emulator doesn't support TLS).
  - Created the missing pull secret and added RBAC for the AAP controller to access it.
  - Switched the network backend to the CI-compatible collection to bypass the OpenStack dependency that doesn't exist in this environment.
  - Relabeled the agent with the correct host type identifier so agent selection could match it.
  - Set the controller availability policy to single-replica mode so etcd could form quorum on a single-node cluster.
- Registered and onboarded a bare-metal worker agent into the OSAC hardware inventory, including VM creation, Ironic provisioning, and discovery ISO boot.

## Risks & Challenges

- The `lifecycle-v3` test cluster has AAP post-install jobs still running — it may take additional time to reach the fully READY state.
- The CI cluster template doesn't configure the CI-compatible network backend or single-replica controller policy by default — these had to be set via environment variable overrides. This is a template configuration gap worth raising with the team.
