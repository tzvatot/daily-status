# Daily Status - 2026-09-06

## Accomplishments

- Merged [osac#646](https://github.com/osac-project/osac/pull/646) for [OSAC-4441](https://redhat.atlassian.net/browse/OSAC-4441) — order-independent ClusterOrder feedback condition mapping. PR passed all CI checks (unit, integration, e2e across caas/bmaas/vmaas), received LGTM and approval, and was merged.
- Validated the PROGRESSING feedback behavior on a real OSAC caas-ci deployment (host karim04), confirming the feedback controller correctly derives the furthest lifecycle stage as conditions arrive in any order. Ran four test scenarios:
  - **T1/T2**: Verified PROGRESSING condition reflects the correct furthest stage when conditions are manually patched on the ClusterOrder.
  - **T3**: Full end-to-end lifecycle validation — watched PROGRESSING advance through real HyperShift control plane boot (`ControlPlaneCreated` → `ControlPlaneAvailable`), confirming the deployed operator image works correctly on a real stack.
  - **T4**: Order-independence confirmed naturally through the asynchronous way the operator sets conditions during real cluster provisioning.
- Set up the caas-ci deployment environment end-to-end: deployed OSAC via Helm, registered a bare-metal worker agent through Metal3/Ironic, and configured the AAP automation to work on a single-node OpenShift host.
- Resolved six deployment blockers during environment setup:
  - Deployed Metal3/Ironic by creating the missing Provisioning resource (required on platform-type-None clusters).
  - Fixed bare-metal host registration by correcting the BMC address scheme from HTTPS to HTTP to match the virtual BMC emulator.
  - Created the missing pull secret and granted the AAP service account the necessary RBAC to access it.
  - Switched the network backend to one that works without OpenStack, since the CI environment has no OpenStack available.
  - Relabeled the registered agent to match by host type identifier rather than name, aligning with how the operator selects agents.
  - Switched the etcd availability policy to single-replica mode so etcd can form quorum on a single-node cluster.

## Risks & Challenges

- The `lifecycle-v3` test cluster has AAP post-install jobs still running — it has not yet reached full READY state and needs continued monitoring.
- The CI cluster template used for testing doesn't configure the network backend or etcd availability policy correctly by default — these required manual environment overrides. This is a template configuration gap worth raising with the team.

Merged and validated the order-independent ClusterOrder PROGRESSING feedback feature ([OSAC-4441](https://redhat.atlassian.net/browse/OSAC-4441)) on a real OSAC deployment, including resolving multiple environment blockers to enable end-to-end lifecycle testing.
