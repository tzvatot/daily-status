# Daily Status - 2026-09-30

## Accomplishments

- Fixed an event-emission bug surfaced in review on [osac#1299](https://github.com/osac-project/osac/pull/1299) ([OSAC-4441](https://redhat.atlassian.net/browse/OSAC-4441)) where early lifecycle events were silently dropped during provisioning; responded to reviewer feedback and pushed the fix, though the PR remains blocked awaiting review.
- Rebuilt and stabilized the single-node test environment end to end — restored the missing worker agent, corrected boot ordering, registered the required host type, rolled a new operator image, and stood up the e2e test harness on the test machine.
- Diagnosed and resolved a chain of environment blockers that prevented provisioning from succeeding: missing cloud DNS credentials in the automation platform, a DNS zone/domain mismatch between the agent's expectations and the records actually created, and a time-synchronization failure on the worker VM. Persisted the credential setup and documented it in the runbook.
- Applied a local-only workaround for an unreliable network-operator readiness check that was timing out the provisioning automation in the virtualized environment, which unblocked a full successful provisioning run (~22 minutes, cluster reaching Ready) followed by a deprovision run.
- Built a status-inspection utility that surfaces every cluster order's phase, associated automation job, and lifecycle events in one view, replacing an earlier narrower script.
- Investigated an e2e assertion failure over a missing intermediate lifecycle event and confirmed the root cause: provisioning stages were being inferred from live control-plane conditions that can flip out of order, so an intermediate stage was genuinely never observed. Reworked the design to emit events directly off the order's own conditions, aligning with the ticket's intent.
- Ran a full validation pass on that rework and found three high-severity issues — duplicate events per milestone, events emitted before the status write they describe (surviving its failure), and a stall watchdog that silently switched off in the final provisioning window. Fixed all three, added regression specs each verified to fail against the commit it fixes plus a drift guard so a future stage cannot disable the watchdog, updated the e2e assertions to the new vocabulary, rebased onto main, cleaned up commit metadata, and opened draft PR [osac#1328](https://github.com/osac-project/osac/pull/1328) stacked on [osac#1299](https://github.com/osac-project/osac/pull/1299).
- Extended the senior reviewer persona with two new review lenses drawn from the bug found this cycle.

## Risks & Challenges

- [osac#1299](https://github.com/osac-project/osac/pull/1299) is blocked with no review; [osac#1328](https://github.com/osac-project/osac/pull/1328) is stacked on it and cannot be marked ready until it merges.
- Integration tests for the new event behavior have not been run — they require a live cluster, so nothing yet exercises these events through a full reconcile against a real hosted cluster.
- No written acceptance criteria or test plan exist for this work, so validation can only assert internal soundness, not story completeness.
- The lifecycle-event assertion helper has no caller in the producing repo and its only consumer lives on a separate branch written against the old event vocabulary. Neither CI can detect the mismatch; it would surface only post-merge in a live e2e run. The two branches need to be diffed before either merges.
- The automation-platform workaround that bypasses the flaky cluster-operator wait remains local and uncommitted on the test machine, with backup files in place — it will be lost on teardown and is not reproducible by anyone else.
- Configuration field names for stall thresholds still use the retired stage vocabulary; renaming them would break existing environment variables, so the inconsistency is deferred.
- The e2e test has not yet been re-run against the new event vocabulary.

## Key Effort

Getting the single-node provisioning e2e path working end to end and correcting how cluster provisioning lifecycle events are derived and emitted.
